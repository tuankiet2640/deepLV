# ADR-001: Core Technology Choices

**Status:** Accepted
**Date:** 2026-04-22

## Context

We need to choose a technology stack for a portfolio-grade machine translation system that:
- Demonstrates production engineering practices
- Runs on any machine via `docker compose up`
- Is inspectable and explainable to a hiring panel
- Delivers real translation functionality, not a mock

## Decisions

### 1. FastAPI for API Gateway

**Chosen over:** Flask, Django, Express, Axum (Rust)

**Rationale:**
- Native async support — critical for non-blocking Redis/DB calls and forwarding to model worker
- Automatic OpenAPI/Swagger docs — the hiring panel gets interactive API documentation for free
- Pydantic validation — request/response schemas are self-documenting and type-safe
- Python ecosystem — required anyway for ML inference, so one language for backend + ML reduces operational complexity

**Trade-off acknowledged:** Python is slower than Rust/Go for raw HTTP throughput. For a translation API where inference dominates latency (300ms+ vs 0.1ms routing overhead), this is irrelevant. The bottleneck is never the web framework.

### 2. MarianMT (Opus-MT) via HuggingFace — Pretrained Models

**Chosen over:** training from scratch, OpenAI API, Google Translate API

**Rationale:**
- Open-source, no API keys or billing — reviewers can run the full system offline
- ~100 language pairs available, reasonable quality for demonstration
- Well-documented, HuggingFace ecosystem integration
- Shows we understand model serving without requiring training infrastructure

**Trade-off acknowledged:** Translation quality is below DeepL/Google. This project demonstrates systems engineering, not NLP research. The architecture would work identically with a fine-tuned model dropped in.

### 3. CTranslate2 for Inference

**Chosen over:** raw PyTorch, ONNX Runtime, TorchServe

**Rationale:**
- 2-5x faster inference than PyTorch on CPU via INT8 quantization
- Lower memory footprint — critical for running multiple models on a single machine
- Simple Python API — `translator.translate_batch()` is one call
- Production-proven (used by OpenNMT)

**Trade-off acknowledged:** adds a model conversion step (PyTorch -> CTranslate2 format). We handle this at build time in the Docker image.

### 4. Redis for Caching and Rate Limiting

**Chosen over:** in-process cache (lru_cache), Memcached, database-backed rate limiting

**Rationale:**
- Shared across API replicas — cache survives restarts and is consistent across instances
- Built-in TTL eviction — no manual cache invalidation logic
- Atomic operations (INCR, EXPIRE) — race-free rate limiting
- Industry standard for this exact use case

**Trade-off acknowledged:** adds a dependency and network hop (~0.5ms). Justified because in-process cache doesn't survive restarts and can't be shared.

### 5. Separate Model Worker Process

**Chosen over:** in-process model loading in the API server

**Rationale:**
- **Isolation:** model OOM or crash doesn't take down the API
- **Scaling:** can run N model workers per 1 API server (or vice versa)
- **Deployment:** update models without API downtime
- **Memory management:** model LRU cache is self-contained

**Trade-off acknowledged:** adds ~1ms network latency per request and operational complexity. Worth it for the architectural clarity and scaling story it demonstrates.

### 6. PostgreSQL for Persistent Storage

**Chosen over:** SQLite, MongoDB, no database

**Rationale:**
- Production-standard relational database
- Alembic migrations demonstrate schema evolution
- JSONB support for flexible usage log metadata
- Connection pooling via asyncpg

**Trade-off acknowledged:** heavier than SQLite for a portfolio project. But using SQLite in a system that claims to be "production-grade" undermines the premise. PostgreSQL is what you'd actually use.

## Consequences

- Full system requires Docker (4 containers: API, worker, Redis, PostgreSQL)
- First startup downloads ~1-2GB of model weights (cached in Docker volume)
- CPU-only inference means single-sentence translation in 200-500ms (acceptable)
- Python-only backend simplifies hiring panel review (one language to read)
