# Multi-provider translation engine with document pipeline, admin dashboard, and observability

This change transforms a single-provider (MarianMT) translation API into a multi-provider platform where users choose how their text gets translated: free built-in models, bring-your-own-key (BYOK) for OpenAI/HuggingFace/Google, or spend credits to use admin-managed keys. On top of that, a document upload pipeline (PDF/DOCX/TXT) parses and translates files in background tasks, an admin dashboard provides user/key/settings management, and a Prometheus+Grafana stack adds production observability. The frontend gains corresponding pages for document translation, provider key management, credits, and admin controls.

Watch for: API keys are stored in plaintext in the database (confirmed). Credits are deducted *after* the document translation completes in the background task, meaning a user with zero credits can still get a full document translated (confirmed). The `asyncio.create_task` background translation runs without exception shielding from the request lifecycle, risking silent loss if the event loop or task is cancelled (likely). The admin N+1 query pattern in `list_users` fires a separate query per user for usage stats (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The provider abstraction is well-designed: an abstract `TranslationProvider` base with per-provider subclasses, and a `ProviderManager` that resolves the right provider instance based on BYOK key presence or admin-credit fallback. However, the credit deduction logic has a timing gap in the document flow where translation happens before the balance check, allowing zero-balance users to get free translations on the admin's dime.

Document translation runs in a detached `asyncio.create_task` with no lifecycle guarantee. If the process restarts, in-flight jobs are lost with no recovery mechanism — they stay stuck in "processing" forever.

API keys (both user BYOK and admin provider keys) are stored as plaintext strings in `encrypted_api_key` columns. The code contains `TODO` comments acknowledging this but ships without any encryption. This is the single most important security gap in this change.

The frontend download flow has a contract mismatch: the API returns JSON but the hook expects a binary blob with Content-Disposition, producing a JSON file instead of translated text. The polling hook has a dependency-array bug that causes interval churn during active jobs.

<details>
<summary>Issues (8)</summary>

1. **Plaintext API key storage** — `encrypted_api_key` columns store raw key text. Encrypt with Fernet or integrate a KMS before shipping; a database breach exposes all user and admin keys.
2. **Credit deduction after translation in document flow** — `DocumentTranslator.translate_document` calls `deduct_credits` after all chunks are already translated. A zero-balance user gets a free translation. Move the credit check (or at minimum a reservation) before the translation loop.
3. **Background task lifecycle** — `asyncio.create_task` in the request handler has no crash recovery. If the process restarts, pending/processing jobs stay stuck. Add a persistent queue (Redis/Celery) or at minimum a startup sweep that marks orphaned jobs as failed.
4. **Admin list_users N+1 queries** — Each user in the list triggers a separate aggregate query for usage stats. Use a joined subquery or window function.
5. **Download endpoint returns JSON, not a file** — `download_translated_document` returns a JSON body with `translated_content` as a string field. The frontend `downloadResult` hook calls `res.blob()` expecting binary content. This will produce a JSON file, not a clean text file with proper Content-Disposition.
6. **Polling loop recreates interval on every render** — `useDocumentTranslation` puts `jobs` in the `useEffect` dependency array, causing the interval to be torn down and recreated on every job list change. This can miss poll windows or double-fire.
7. **Credit race condition** — `deduct_credits` reads `user.credits_balance` in Python, subtracts, and writes back without a database-level lock. Two concurrent requests can both pass the balance check and overdraw.
8. **No input validation on admin settings values** — `update_settings` accepts arbitrary strings for numeric settings like `credit_cost_per_1k_chars`. A typo (e.g., "abc") will silently store an invalid value that fails at runtime when parsed.

## Provider resolution and credit deduction timing

The text translation endpoint in `translate.py` correctly calls `deduct_credits` *before* invoking the provider, returning HTTP 402 if the balance is insufficient. The document endpoint has a different — broken — order. In `DocumentTranslator.translate_document`:

```python
# Translation happens first (all chunks)
for i, chunk in enumerate(chunks):
    translated = await provider.translate(...)

# Credits deducted afterward
if not provider_key_id and job.provider != "marianmt":
    credit_ok = await self.provider_manager.deduct_credits(...)
    if not credit_ok:
        log.warning("insufficient_credits_for_document", ...)
        # Still save result since translation was already done
```

A user with zero credits submits a document translation using an admin key, gets the full translated output, and the debit fails silently. The provider (OpenAI, Google) has already been billed on the admin's dime. This needs a pre-translation credit reservation that estimates cost based on character count from the parsed document.

## Background task reliability

The document upload endpoint launches translation via a bare `asyncio.create_task` that:

- Creates its own database session via `async_session()`
- Is not tracked by any task registry
- Has no crash recovery path

If the API process crashes or is restarted while jobs are in "processing" state, those jobs remain stuck forever. Nothing drives the `processing -> failed` transition on abnormal termination. For production, this should go through a persistent task queue (Redis-backed with Celery/ARQ/Dramatiq) or at minimum a startup health check that sweeps `processing` jobs older than a timeout and marks them failed.

## Plaintext credential storage

Both `ProviderKey.encrypted_api_key` and `AdminProviderKey.encrypted_api_key` store the raw API key string:

```python
# src/api/routers/providers.py line 86
provider_key = ProviderKey(
    ...
    encrypted_api_key=req.api_key,  # TODO: encrypt with Fernet/KMS
    ...
)
```

The same pattern appears in `admin.py` for admin keys. The column *name* implies encryption, but no encryption occurs. A database read (SQL injection, backup exposure, insider access) reveals every OpenAI/HuggingFace/Google key stored by users.

## Admin N+1 and download endpoint mismatch

The `list_users` endpoint iterates over fetched users and fires a per-user aggregate query:

```python
for user in users:
    stats_result = await db.execute(
        select(...).where(UsageLog.user_id == user.id)
    )
```

With 200 users (the max page size), this fires 201 queries. A subquery join would reduce this to 1-2 queries.

The download endpoint (`GET /documents/jobs/{job_id}/download`) returns a `DocumentDownloadResponse` Pydantic model as JSON. The frontend hook does:

```typescript
const blob = await res.blob();
const url = URL.createObjectURL(blob);
a.download = filenameMatch ?? `translated-${jobId}.txt`;
```

It reads a `Content-Disposition` header that the API never sets, falls back to a `.txt` filename, and saves the JSON blob as a text file. The result is a file containing `{"job_id": "...", "translated_content": "..."}` — not the clean translated text the user expects. The endpoint should return a `PlainTextResponse` or `StreamingResponse` with `Content-Disposition: attachment`.

## Frontend polling loop instability

In `useDocumentTranslation.ts`, the `useEffect` that starts the polling interval includes `jobs` in its dependency array:

```typescript
useEffect(() => {
    refreshJobs();
    pollIntervalRef.current = setInterval(() => {
        const hasActive = jobs.some(j => j.status === "pending" || j.status === "processing");
        if (hasActive) { refreshJobs(); }
    }, 3000);
    return () => { clearInterval(pollIntervalRef.current); };
}, [refreshJobs, jobs]);
```

Every time `refreshJobs` updates `jobs`, the effect re-runs: clears the old interval, calls `refreshJobs()` again immediately (triggering another state update), and sets a new interval. This creates a feedback loop where polling restarts every 3 seconds at best, and at worst fires multiple refreshes during active job processing. The fix is to check `jobs` via a ref inside the interval callback rather than re-registering the effect.

## Credit balance race condition

`ProviderManager.deduct_credits` does an optimistic Python-level check:

```python
if user.credits_balance < cost:
    return False
user.credits_balance -= cost
```

Two concurrent requests can both read a balance of 5.0, both pass the check (each needing 3.0), and both write `2.0` — overdrawing the account. The fix is a `SELECT ... FOR UPDATE` on the user row or an atomic `UPDATE users SET credits_balance = credits_balance - :cost WHERE credits_balance >= :cost`.
