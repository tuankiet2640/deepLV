# Multi-provider translation engine v2 — all v1 issues addressed

This second pass reviews the fixes applied to the 8 issues surfaced in v1. The codebase now encrypts API keys at rest via Fernet, deducts credits before translation in the document pipeline, sweeps orphaned jobs on startup, uses a subquery join for the admin user list, returns `PlainTextResponse` with `Content-Disposition` from the download endpoint, uses a ref-based polling strategy in the frontend hook, performs atomic credit deduction via `UPDATE ... WHERE balance >= cost`, and validates numeric admin settings server-side.

Watch for: The `purchase_credits` endpoint adds credits via a non-atomic `user.credits_balance += req.amount` pattern — same race class the v1 deduction fix addressed, but in the additive direction (confirmed). The `asyncio.create_task` background task still has no task reference tracking, meaning unhandled exceptions outside the inner try/except are silently swallowed (confirmed). The encryption module re-instantiates `APISettings()` on every encrypt/decrypt call (confirmed, minor perf).

**Verdict**: APPROVED

## High-level view

All 8 v1 issues are resolved. The Fernet encryption uses SHA-256 key derivation from a configurable secret — sound for at-rest protection of BYOK keys. Credit deduction in the document pipeline now happens before any translation work begins, failing the job early if the balance is inadequate.

The startup sweep marks both "processing" and "pending" jobs as failed on restart, closing the lifecycle gap without requiring a persistent queue. The admin user listing performs a single outerjoin against a usage-stats subquery. The frontend polling hook reads jobs through a ref inside the interval callback, keeping the effect dependency array stable.

Three new minor concerns emerged from the fixes: a non-atomic credit addition (same race pattern as v1 #7 but in the additive direction), per-call settings parsing in the encryption module, and a bare `asyncio.create_task` that drops exceptions outside its inner handler. None are blocking.

## Non-atomic credit addition

The `purchase_credits` endpoint at `credits.py:68` does:

```python
user.credits_balance += req.amount
```

Two concurrent purchase requests for the same user can both read balance `10.0`, both compute `10.0 + 50.0 = 60.0`, and both write `60.0` — losing one of the two `50.0` additions. The user pays twice but only gets credited once. The fix is the same atomic pattern used in `deduct_credits`:

```python
await db.execute(
    update(User)
    .where(User.id == user.id)
    .values(credits_balance=User.credits_balance + req.amount)
)
```

Less critical than the overdraw race (bookkeeping bug, not security hole), but should be fixed for correctness.

## Background task observability gap

The document upload handler calls `asyncio.create_task(...)` without storing the returned `Task` object. The internal try/except in `translate_document` catches translation errors and marks jobs failed — that path works. The gap is narrower: if the database fetch of `job` or `user` inside `_run_translation_background` raises (e.g., connection timeout), the exception vanishes silently since Python only logs "Task exception was never retrieved" in asyncio debug mode. Storing the task reference and adding a done-callback would close this.
